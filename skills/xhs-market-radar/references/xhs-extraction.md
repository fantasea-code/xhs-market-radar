# 小红书抽取协议

目标是拿到能支持市场判断的证据，而不是批量抓取。

## 搜索和预筛

围绕 idea 生成搜索词：

- 产品名：已有竞品、别名、英文名、中文名。
- 场景词：用户在什么情况下需要它。
- 痛点词：不好用、太麻烦、求推荐、平替、替代、吐槽。
- 交易词：怎么买、链接、价格、会员、内测、邀请码。
- 教程词：怎么设置、自动化、工作流、搭建、开发者。

预筛记录：

- URL
- 标题
- 作者
- 发布时间
- 互动数据：赞、藏、评论，缺失则写未记录
- 笔记形态：图文 / 视频 / 搜索结果 / 不可访问
- 正文摘要
- 标签
- 评论概览
- 与当前 idea 的关系

## 详情页访问和复盘

访问小红书详情时，优先模拟真实阅读路径：搜索关键词 -> 识别目标笔记 -> 点击搜索结果 -> 等正文/评论/图集加载 -> 翻图或播放关键片段 -> 再抽取证据。

常见访问失败类型：

- 直达详情 URL 失效、缺少当前 `xsec_token`、打开后 404 或提示到 App 查看。
- 搜索结果页和详情浮层混在同一页面，Agent 只读到搜索列表，没读到右侧/浮层详情。
- 图集懒加载未触发，DOM 只枚举到当前图，Network 里也没有后续图片。
- 图片请求发生在 Network 记录之前，需要刷新详情页或重新翻图。
- CDN URL 用 `curl`、`Invoke-WebRequest` 或脚本直连失败，但真实浏览器已经能正常显示。
- Network 里混有搜索缩略图、头像、评论图片和推荐流图片，误判为当前笔记原图。
- 视频帖默认只能稳定读取页面正文、标签、评论和关键帧；只有实际完成字幕 OCR 或 ASR，才能作为完整视频内容证据。

处理顺序：

1. 直达失败时，用标题/作者/产品名重新站内搜索，并从搜索结果自然点击进入详情页。
2. 打开后先确认当前详情标题、作者、正文和 URL 是否匹配目标笔记。
3. 图文帖先翻完图集，记录页面总数，例如 `3/10` 的 `10`；再决定保存哪些关键图。
4. 图片优先从真实浏览器已加载的 DOM、页面数据结构或 Network response body 保存；不要先用外部脚本直连 CDN。
5. 如果 Network response 保存失败，尝试浏览器原生复制/保存图片；仍失败再做单图元素截图，并标注“元素截图”。
6. 如果只能页面截图，必须写“页面截图”，并降低该参考证据等级。
7. 每个失败点只在 Agent 执行过程中自检，不要求写入最终报告，也不要求单独落盘。最终报告只写读者能理解的证据状态或参考不足原因，不写访问路径、保存方式、Network、CDN、DevTools、脚本等执行方法。

完成门槛：

- 高价值参考如果还写着“图集未完整浏览”“后续应补关键原图”“仅页面截图”，报告只能算草稿，不能给出 A 级证据。
- 已打开详情页但图片/视频证据不完整，最高只能给 B；只有搜索结果或标题，最高只能给 C。
- 图文帖若图片里是长文、价格、参数、流程或吐槽，而未读图/OCR，不能基于正文或标题下强结论。
- 临时拼装替代方案的失败要写清楚“它为什么只是替代方案”，不能直接外推成专用产品需求失败。
- 最终报告面向市场/产品读者，不面向执行 Agent；不要暴露底层抓取和保存动作，只呈现证据内容、完整性和判断贡献。

## 深挖高价值笔记

高价值信号：

- 评论区出现求链接、求教程、求内测、问价格。
- 评论区出现强吐槽、替代方案、真实失败场景。
- 图文包含产品流程、价格、参数、功能对比、购买路径。
- 视频展示了实际产品使用、交易引流或用户反馈。
- 能证明“已有产品没解决好”或“用户愿意折腾/付费”。

先给参考对象分类：

- 专用竞品：为当前场景设计的产品，例如生活记录硬件、专用 App、垂直 SaaS。
- 临时拼装替代方案：用户用通用工具硬凑当前场景，例如用普通麦克风、通用录音笔、快捷指令、表格、Notion 模板自建流程。
- 相邻竞品：解决部分场景但定位不同，例如会议录音卡、运动相机、普通智能手表。

判断规则：

- 专用竞品的真实测评、退货、续费、长期使用反馈，优先用于判断需求是否成立。
- 临时拼装替代方案的痛点，优先解释为“现有流程不够闭环/专用产品机会”，不能直接解释为“需求不存在”。
- 只有当专用竞品和临时替代方案都缺少购买、复用、求链接、求教程、正反馈时，才考虑“疑似伪需求”。

高价值图文帖：

- 优先保存小红书图文帖本身的原图；页面截图不能替代原图。
- 对高风控社媒，不要把 `curl`、`Invoke-WebRequest`、脚本直连 CDN 当成首选。先让真实浏览器通过站内自然路径打开详情页、翻图、触发图片加载，再从当前页面或 Network 中提取证据。
- 先浏览/粗读完整图集，再决定保存哪些关键图。不要为了证明“看过”而把低信息量图片全部下载并塞进报告。
- 优先保存关键图：长文页、价格/参数页、操作流程、功能对比、吐槽页、评论截图、交易路径、关键产品画面。
- 低信息量图片可以不保存：重复摆拍、纯氛围图、无文字封面、无新增信息的产品外观图；但要记录“已浏览，未嵌入原因”。
- 记录图集处理状态，例如 `已浏览 10/10，保存关键图 3/10`。
- 每张证据图写一句摘要，不做冗长图集审计。
- 必须读取图片里的文字和画面信息。小红书图文经常把长文、价格、参数、步骤、对比、吐槽和评论截图放在图片里；这些内容要进入判断，不能只读正文。
- 最终参考条目里单独写 `图片文字/画面证据`，概括每张关键图的贡献。

图集审阅要求：

- 记录页面显示总图数，例如 `2/10` 中的 `10`。
- 记录 DOM 初始枚举数、翻图后枚举数、最终枚举数。
- 浏览/粗读所有图片，判断每张图是否有新增证据价值。
- 保存 `image-01` 到 `image-M`，只保存关键图；除非用户要求“完整归档”，否则不默认全量落盘。
- 每张已保存图片都要有本地图片路径和读图摘要；未保存图片要写总数和不保存原因。
- 最终报告必须在对应参考条目下直接嵌入图片；不要只写本地目录。

完整性判定：

- `完整审阅`：页面显示总图数 = 已浏览/粗读数；关键图已保存并有摘要。保存数可以小于总图数。
- `部分审阅`：总图数和已浏览数不一致，或部分关键图没有读图摘要。
- `未验证`：无法确定总图数，只能枚举当前 DOM 图片。

降级规则：

- 高价值图文帖如果没有完成全图浏览/粗读，只能写 B 或 C，不能写 A。
- 已完成全图浏览/粗读但只保存关键图，可以给 A；必须写清 `已浏览 N/N，保存关键图 M/N` 和未保存原因。
- 如果只保存页面截图，必须标注为“页面截图”，不能写成“原图证据”。
- 如果图片里明显是长文但未 OCR/读图，必须把该条列为“证据不足”，不能基于标题或正文下强结论。
- 如果浏览器已加载图片但外部下载失败，优先使用 DevTools Network response body、浏览器原生复制/保存图片、单图元素截图；不要反复用脚本直连 CDN 重试。

图片保存优先级：

1. 真实浏览器已加载的图文原图：从当前 DOM、页面数据结构或 Network response body 保存。
2. 小红书原生交互：右键复制/保存图片，或等价的浏览器原生图片保存能力。
3. 单图元素截图：无法保存原图但画面清晰时使用，并标注为“元素截图”。
4. 页面截图：只用于证明上下文、评论区或异常状态，不作为高价值图文的首选读图证据。
5. 外部 HTTP 下载：只在图片 URL 已由真实浏览器加载、并且需要落盘复查时尝试一次；失败后记录原因并换浏览器侧证据，不继续模拟批量下载。

高价值视频帖：

- 记录标题、正文、标签、互动数据、评论。
- 如需视频全文或口播证据，按 `references/video-evidence.md` 的三层集成和首次启用确认执行。
- 默认处理层级是：页面正文和标签 -> 评论区 -> 关键帧画面。这个层级不能声称已理解完整视频。
- 如果拿不到可复用的视频源，或用户不允许临时处理视频文件，只能写“未提取视频全文”。
- 如果视频关键判断来自画面字幕、操作演示或口播，必须实际完成关键帧 OCR、字幕提取或 ASR 后才能写成证据；否则只能写“待验证”。
- 视频证据要分层标注：页面正文、评论区、关键帧画面、字幕 OCR、ASR 口播、未验证推断。
- 不要把“计划做 ASR”写成“已经做了 ASR”。没有跑完就不能用 ASR 结果支撑结论。

## 评论区优先级

评论比正文更接近真实需求。优先记录：

- 购买/交易：在哪里买、多少钱、求链接、求内测、邀请码。
- 痛点/失败：不好用、同步失败、转写差、太贵、太麻烦。
- 替代方案：别人推荐的 App、硬件、快捷指令、手工流程。
- 作者回复：交易路径、开发进度、限制、定价、私域。

## 不参与结论的内容

- 只有标题相关，正文不支持当前判断。
- 纯娱乐、泛泛种草、无评论反馈。
- 互动极低且没有技术/痛点信息。
- 无法打开且没有可复查内容。
